# 東京電力 チャットボット機能 デザイン分解ドキュメント

対象: 東京電力グループのカスタマーサポート用チャットボット
調査日: 2026-07-08

> **本デモへの反映:** 本書は調査メモである。社内ナレッジAIデモへ取り込む UX 原則・パターン・契約の正本は  
> [`internal_knowledge_conversation_ux.md`](./internal_knowledge_conversation_ux.md) とする。  
> サイト埋め込みランチャーや LINE トークUIそのものは移植対象外。選択式進行・知覚速度・見やすさ・行き止まりゼロのみ採用する。

東京電力のチャットボットは **2社2系統** に分かれている点がまず構造上の特徴。

| 系統 | 運営会社 | 役割 | 主な用件 |
|---|---|---|---|
| ① サポートAI（サイト埋め込み型） | 東京電力エナジーパートナー（EP） | 小売（契約・料金） | 契約照会、料金・使用量確認、支払い、引越し |
| ② LINE / Webチャット | 東京電力パワーグリッド（PG） | 送配電（インフラ） | 停電、電柱・電線・設備トラブル |

---

## 1. 全体アーキテクチャ

### 1.1 チャネル構成

```
ユーザー
 ├─ EPサイト（tepco.co.jp/ep）
 │   └─ 画面右下 フローティングチャットランチャー
 │       ├─ AIチャットボット（24時間）
 │       └─ 有人チャットオペレーター（時間帯限定）
 │
 ├─ PGサイト（tepco.co.jp/pg）
 │   └─ 専用ページから起動する Webチャット（24時間）
 │
 └─ LINE 公式アカウント「東京電力パワーグリッド コンタクトセンター」
     └─ LINEトーク画面内チャットボット（24時間）
```

### 1.2 技術・運用基盤（公開情報より）

- EP側は **Zendesk** をサポート基盤のハブとして採用。チャット、有人対応、Slack連携（オペレーター→管理者へのエスカレーション用「#教えて管理者」チャンネル）を統合
- AIチャットボット・AIエンジンは Zendesk の API 連携で接続
- FAQ検索にもAIを活用し、チャットボットと同一のナレッジ圏を形成
- 電話側はボイスボット（AI音声自動応答）と連動し、チャネル横断のオムニチャネル設計
- AIチャット満足度 90% 以上と公表（EP DX推進室）

### 1.3 責務分離の設計思想

- 「契約・料金」と「停電・設備」で**入口を完全に分離**。PG側チャットには「契約に関する問い合わせは小売電気事業者へ」と明示的なリダイレクト文言を配置
- ユーザーの誤流入を前提とし、各入口で「ここで出来ること／出来ないこと」を先に提示する防御的設計

## 2. ページ構成（IA / 導線設計）

### 2.1 EP側：カスタマーセンターページ

```
カスタマーセンターページ
├─ ヘッダー（グループ共通）
│   ├─ グループ会社クイックリンク（HD/FP/PG/EP/RP の5社切替）
│   ├─ ログイン（くらしTEPCO web / ビジネスTEPCO）
│   ├─ サイト内検索
│   └─ グローバルナビ（電気/ガス/引越し/くらしTEPCO/手続き/法人/企業情報）
├─ 重要なお知らせ帯（混雑告知・休業案内）★チャットへの誘導文を含む
├─ 「このようなお手続きが可能です」プリセット用件ウィジェット
│   └─ ボタン: 契約内容の確認 / 支払いしたい / 未払い料金の確認
│       （breakpoint 769px で PC/SP 出し分け設定を持つ JSON 定義）
├─ 電話窓口情報（受付時間・混雑注意・IVR案内）
├─ Web手続きへの導線（24時間訴求）
└─ 画面右下: チャットランチャー（フローティング・全ページ共通）
```

**導線設計のポイント**
- 電話の混雑告知が同時に**チャットへの誘導装置**として機能（「画面右下のチャットをご利用ください」を複数箇所で反復）
- チャット起点は「専用ページ」ではなく**全ページ常駐のランチャー**。問い合わせ意図が発生した瞬間の離脱を防ぐ
- プリセット用件ボタンで「何を聞けばいいか分からない」状態を解消（空白状態の設計）

### 2.2 PG側：チャット案内ページ

```
停電・電気設備チャットページ
├─ ページ内アンカーナビ（LINEチャット / webチャット の2タブ構成）
├─ 「24H 全日24時間受付」アイコンバッジ（最上部で受付時間を即答）
├─ LINE友だち追加バナー（推奨チャネルとして最上位配置）
├─ LINE追加手順（3パターン × 各4ステップのスクショ付きガイド）
│   ├─ QRコード追加
│   ├─ ID検索追加（@tepcopgcc）
│   └─ アカウント名検索追加
├─ 契約系問い合わせのリダイレクト注記（小売事業者一覧へ外部リンク）
├─ Webチャット起動ボタン「チャットでお問い合わせする」
├─ 受付内容の明示（対応できる用件リスト）
│   └─ 停電情報に無い停電 / 鳥の巣・フン害 / 樹木接触 / 電柱敷地料 など
├─ 「当社の電気設備とは」図解（鉄塔・送電線・変電所・電柱・電線）
├─ 利用規約リンク（PDF・同意前提）
└─ 注意事項アコーディオン
    ├─ 混雑時は受付時間内でも利用不可の場合あり
    ├─ 個人情報は当社要請時のみ入力
    ├─ 無応答一定時間でチャット自動終了
    ├─ チャット内容のSNS転載禁止
    └─ ネットワーク切断リスク
```

**導線設計のポイント**
- LINEを第一推奨、Webチャットを「アプリ登録不要」の代替として位置づけるチャネル優先順位
- 追加手順を実機スクショで4ステップ分解 → 高齢者を含む幅広い層に対応
- 「対応できる用件」を図解込みで先出しし、期待値を起動前に調整

## 3. UIデザイン分解

### 3.1 チャットランチャー（EP）

| 要素 | 仕様・特徴 |
|---|---|
| 位置 | 画面右下固定（フローティング） |
| 表示範囲 | サイト全ページ常駐 |
| 形状 | 円形アイコンボタン（吹き出しモチーフ） |
| 誘導 | ページ本文・告知帯から「画面右下のチャット」と文言参照 |
| プロアクティブ提案 | プリセット用件ボタン（契約内容の確認 等）をウィジェットとして表示。PC/SPで出し分け（breakpoint 769px） |

### 3.2 チャットウィンドウ（EP サポートAI）

| 要素 | 仕様・特徴 |
|---|---|
| 会話形式 | ボット吹き出し（左）＋ ユーザー吹き出し（右）の標準チャットUI |
| 入力手段 | ①選択肢ボタン（カテゴリドリルダウン）②フリーテキスト入力の**ハイブリッド** |
| カテゴリ導線 | 例: 「料金・支払全般」→「料金・使用量の確認をしたい」→「利用料金および使用量の確認をしたい」の3階層 |
| キーワード導線 | 「電気料金を教えて」「使用量を教えて」「料金」「使用量」等の短文で同一フローに合流 |
| 展開UI | 「▼」タップで補足説明を展開（アコーディオン） |
| 認証UI | 会話中に**くらしTEPCO webログイン画面をポップアップ**表示。メール＋パスワードでログイン |
| 認証スキップ | ポップアップの「×」で閉じると、チャット内質問（契約住所＋お客さま番号 or 電話番号）による代替本人確認へフォールバック |
| 画像 | 手順説明画像はクリックで拡大表示 |

### 3.3 チャットUI（PG Webチャット / LINE）

| 要素 | 仕様・特徴 |
|---|---|
| 起動 | ページ内ボタン「チャットでお問い合わせする」／LINEトーク |
| LINE側 | トーク画面のリンクから停電情報サイトへ遷移可能（ボット↔情報サイトの相互導線） |
| 受付時間表示 | 「24H」アイコンバッジで視覚的に即答 |
| 規約同意 | 利用開始前に利用規約（PDF）への同意を前提化 |
| セッション制御 | 一定時間無応答で自動終了する旨を事前明示 |

### 3.4 ビジュアルデザイン傾向

- グループ共通のコーポレートデザイン（TEPCOロゴ、5社切替ヘッダー）にチャットUIを従属させる構成
- 「24H」バッジ、指クリックアイコンなど、**受付時間と操作可能性をアイコンで即時伝達**
- ステップガイドは番号＋実機スクショの反復パターンで統一
- 設備説明にはイラスト図解を使用（テキスト定義を避ける）

## 4. UXデザイン分解

### 4.1 会話フロー設計

```
起動
 └─ 用件特定（2ルート合流型）
     ├─ ルートA: カテゴリボタンをドリルダウン（最大3階層）
     └─ ルートB: フリーテキストのキーワード認識
 └─ 本人確認が必要な用件か判定
     ├─ 不要 → FAQ回答・ページ誘導で完結
     └─ 必要 → 認証フェーズへ
         ├─ 優先: くらしTEPCO ログイン（ポップアップ）
         └─ 代替: チャット内で契約住所＋お客さま番号/電話番号を聴取
 └─ 回答提示（料金・使用量・契約内容・手続き実行）
 └─ 解決しない場合 → 有人チャットオペレーターへエスカレーション（受付時間内）
```

### 4.2 UX上の設計判断（分析）

1. **選択肢×自由入力のハイブリッド**
   初心者はボタン、リピーターはキーワード直打ちで同じゴールに到達できる。学習コストと操作速度を両立。

2. **認証の段階的フォールバック**
   ログイン（強い認証・体験最速）を第一候補にしつつ、非会員・パスワード忘れユーザーを属性照合（弱い認証）で救済。**離脱ポイントになりがちな認証で行き止まりを作らない**。

3. **限界の事前開示**
   「契約者本人でない場合」「1か所に複数契約がある場合」はAIが確認できないと明記。AIの失敗を体験内で予告し、期待値崩壊を防ぐ。

4. **チャネル間の役割分担と相互送客**
   電話混雑 → チャットへ誘導 / チャット限界 → 有人・電話へ / 契約系誤流入 → 小売事業者へ。行き止まりのないネットワーク型導線。

5. **プロアクティブ設計**
   ページ文脈（カスタマーセンター）に応じたプリセット用件ボタンを先出しし、ゼロ入力で会話を開始できる。

6. **信頼・安全設計**
   個人情報は「当社要請時のみ入力」と制限、SNS転載禁止、無応答自動終了、規約同意。BtoC大規模サービスとしてのリスク管理をUX文言に組み込み。

7. **24時間×有人時間帯の二層構造**
   ボットで24時間の一次受けを保証し、有人リソースは限定時間に集中。数値効果として電話対応時間約3割削減（ボイスボット併用時）を公表。

### 4.3 ペルソナ配慮

- 高齢ユーザー: LINE追加手順のスクショ4ステップ分解、電話窓口の並存
- 緊急ユーザー（停電）: PG側は用件を停電・設備に絞り、24時間即応
- 手続き慣れユーザー: キーワードショートカット、Web手続きへの直リンク

## 5. 情報設計上の特徴まとめ

| 設計原則 | 実装例 |
|---|---|
| 責務の分離 | EP（契約・料金）と PG（停電・設備）で入口・ボットを分割 |
| 期待値の事前調整 | 「出来ること」リスト、AIの限界明示、受付時間バッジ |
| 行き止まりゼロ | 認証フォールバック、有人エスカレーション、他社リダイレクト |
| ゼロ入力開始 | プリセット用件ボタン、カテゴリドリルダウン |
| チャネル冗長化 | チャット／LINE／電話／Web手続きの相互補完 |
| 防御的文言設計 | 個人情報入力制限、転載禁止、自動終了予告 |
