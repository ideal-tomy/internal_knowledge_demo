# 1. 背景

多くの企業では、就業規則、勤怠細則、経費精算規程、情報セキュリティ規程、稟議・承認権限規程、各種申請マニュアルなどが個別に整備されている。

一方で、実際の業務上の質問は、単一の規程だけでは解決できないことが多い。

例:

- 在宅勤務日に子の看護が必要になった場合、どの休暇区分と勤怠申請を使うか
- 出張中に領収書を紛失した場合、旅費規程と経費精算規程のどちらに従うか
- 緊急購入を行いたい場合、購買規程と承認権限規程上、誰の承認が必要か
- 顧客資料を生成AIで処理したい場合、情報セキュリティ規程上どこまで許可されるか

社員は、複数の文書を探し、該当箇所を読み、条件や例外を照合し、最終的な行動を判断しなければならない。

本デモでは、情報量の少ないFAQサンプルではなく、実際の企業が運用している規程群に近い、相互参照と例外条件を含む高密度なサンプルナレッジを用意する。

ユーザーは質問する前に各文書の内容を確認でき、その後、AIが選択されたナレッジのみを参照しながら、複数文書を横断して回答する体験を行う。

---

# 2. デモのコンセプト

> **複数の規程・細則・マニュアルを事前に確認したうえで質問し、AIがそれらの情報だけを横断的に照合して、結論・根拠・次の手続きを素早く提示する体験を提供する。**

本デモは、単なる「社内質問チャット」の便利さだけを見せるものではない。

AIが業務ワークフローへ組み込まれた場合に、次のような役割を担えることを可視化する。

```text
業務上の入力
↓
関連規程の特定
↓
条件・例外・優先関係の照合
↓
判断結果
↓
根拠提示
↓
次に行う申請・確認・連絡
```

# 3. このデモで証明すること

## 3.1 情報量の多いナレッジを扱えること

短いFAQではなく、章・条項・例外・承認条件・関連文書を持つ複数の規程を対象にする。

ユーザーが「AIに何を与えているか」を事前に閲覧できる状態にし、回答の価値を理解しやすくする。

## 3.2 指定された情報だけを参照すること

AIは、デモで選択されたナレッジパックと会話内で明示された情報だけを根拠として回答する。

一般知識だけで不足部分を補完したり、規程に存在しない社内ルールを推測したりしない。

## 3.3 複数文書を横断して回答できること

単一文書の該当箇所を返すだけではなく、複数の規程に分散した条件を照合する。

回答では、参照した文書、条項、適用条件、例外、情報不足を明示する。

## 3.4 正確性を確認できること

回答本文だけでなく、次を確認可能にする。

- 参照した文書名
- 章・条項・見出し
- 該当箇所の抜粋
- どの情報が結論に使われたか
- 情報が不足している場合の確認事項

## 3.5 ワークフロー内でのAIの振る舞いを可視化すること

回答結果を会話文だけで終わらせず、業務処理に接続可能な構造として表示する。

```text
結論
判断条件
確認した規程
必要な申請
承認者・担当部署
期限
不足情報
推奨する次のアクション
```

これにより、将来の本番開発で、チャットUI以外にも申請画面、社内ポータル、問い合わせ受付、承認フロー、FAQ、ヘルプデスクなどへAIを組み込めることを具体的に想像できる状態にする。

# 4. 対象ユーザー

## 4.1 Primary User

- 総務・人事・労務担当者
- 情報システム担当者
- 社内DX推進担当者
- 業務改善責任者
- 管理部門責任者

## 4.2 Secondary User

- 一般社員
- 拠点責任者
- 部門マネージャー
- 社内ヘルプデスク担当者
- 経営者・決裁者

## 4.3 商談上の対象

- 社内規程やマニュアルが多く、検索性に課題がある企業
- 社内問い合わせの負担が大きい企業
- AIチャットボットの導入効果を具体的に確認したい企業
- AIを業務フローへ組み込む方法を検討している企業
- RAGや社内検索の説明だけでは導入後を想像しにくい企業

# 5. 主要な利用シーン

## 5.1 社内問い合わせ対応

社員の質問に対して、関連規程を特定し、根拠付きで回答する。

## 5.2 複数規程の照合

一つの質問に対して、勤怠、休暇、在宅勤務、経費、承認権限など複数文書の条件を統合する。

## 5.3 手続き案内

回答後に、必要な申請、提出期限、承認者、必要書類、問い合わせ先を案内する。

## 5.4 判断補助

ルール上の適用可否を整理し、断定できない場合は不足情報と確認先を提示する。

## 5.5 ワークフロー連携イメージ

AIの構造化結果を、申請フォームの初期値、担当部署への振り分け、承認経路の選択、アラート表示などへ利用できることを示す。

# 6. 体験設計

## 6.1 基本フロー

```text
1. デモを開く
2. サンプル会社とナレッジパックの概要を見る
3. 文書一覧から各規程を開く
4. 目次・主要ルール・本文を確認する
5. ガイド質問を選ぶ、または自由入力する
6. AIが関連文書を検索・照合する
7. 結論と業務上の次のアクションを見る
8. 根拠文書と該当箇所を確認する
9. 条件を変えて再質問する
```

## 6.2 最重要体験

ユーザーが、回答前にサンプルナレッジを確認していることを前提とする。

そのうえで、AIが数秒で複数文書から必要な情報を抽出し、横断的に照合した結果を返すことで、人が同じ確認作業を行う場合との差を体感できるようにする。

## 6.3 ガイド質問

初回ユーザーが性能を確認しやすいように、質問を難易度別に用意する。

### Level 1: 単一文書確認

- 有給休暇の申請期限はいつですか
- 在宅勤務は週に何日まで可能ですか

### Level 2: 複数文書照合

- 出張中に領収書を紛失した場合、精算には何が必要ですか
- 在宅勤務日に子の看護で午前休を取り、午後から勤務できますか

### Level 3: 判断と次の処理

- 10万円の業務ツールを今日中に緊急購入する場合、誰の承認と何の申請が必要ですか
- 顧客の契約書を外部の生成AIへアップロードして要約してよいですか

## 6.4 Conversation UX（選択式・見やすさ・次の一手）

操作品質の詳細正本は`internal_knowledge_conversation_ux.md`とする。

本デモはサイト併設やLINE表示を行わないが、次の体験品質を必須とする。

1. **ゼロ入力開始:** 起動直後にカテゴリ選択から質問を始められる
2. **ハイブリッド入力:** 選択式と自由文が同じ回答構造へ合流する
3. **最大3階層の絞り込み:** カテゴリ → シナリオ → 具体質問／条件
4. **結論先出し:** 回答先頭で判定ステータスと結論が見える
5. **行き止まりゼロ:** 回答後に Follow-up、不足時は選択肢で追加確認できる

難易度別ガイド質問（6.3）は廃止せず、Intent Treeの葉および質問メタデータとして再利用する。

# 7. サンプルナレッジ要件

## 7.1 基本方針

- 実在企業の文書をそのまま利用しない
- 架空企業の規程として作成する
- 実務で起こりうる条件、例外、期限、金額、承認者、関連文書を含める
- 文書間に明示的な相互参照を設ける
- 単純なキーワード検索だけでは回答しにくい質問を含める
- 回答根拠を人間が検証できるようにする

## 7.2 必須文書

初期サンプルパックには、最低限次の文書を含める。

1. 就業規則
2. 勤怠・休暇運用細則
3. 在宅勤務規程
4. 出張・旅費規程
5. 経費精算・購買規程
6. 稟議・承認権限規程
7. 情報セキュリティ・生成AI利用規程
8. 相談・事故・緊急時対応ガイド

詳細は`internal_knowledge_sample_data_spec.md`で定義する。

## 7.3 情報量

目標値:

- 8文書
- 50〜80セクション
- 合計40,000〜70,000日本語文字
- 文書間参照15件以上
- 条件分岐を含む検証質問20件以上

# 8. 機能要件

## FR-001 ナレッジパック概要表示

デモ開始時に、対象となる架空企業、文書数、カテゴリ、更新日、収録内容を表示する。

## FR-002 文書一覧表示

各文書について、次を表示する。

- 文書名
- バージョン
- 施行日
- 所管部署
- 概要
- 主要トピック
- 関連文書

## FR-003 文書事前閲覧

質問前に各文書の本文を閲覧できる。

必須機能:

- 目次
- 見出し単位の移動
- 本文表示
- 文書内検索
- 関連文書への移動
- 主要ルールの要約表示

## FR-004 ナレッジ選択状態の表示

AIが参照可能な文書を常に画面上で確認できる。

初期版では、サンプルパック内の全規程を横断検索対象とする。

## FR-005 ガイド質問

単一文書確認、複数文書照合、判断・手続き案内の3種類を用意する。

## FR-005a Intent Rails / Guided Drill-down

起動時にカテゴリボタン（Intent Rails）を表示し、最大3階層のドリルダウンでガイド質問へ合流できる。

詳細は`internal_knowledge_conversation_ux.md`のP01/P02。

## FR-005b Follow-up Chips / Clarifying Choice

回答後に次アクション用チップを提示する。情報不足時は、可能な範囲で選択肢により追加確認する。

詳細は同仕様のP06/P07。

## FR-006 自由質問

ユーザーが自然文で質問できる。ドリルダウン表示中もComposerから送信できる。

## FR-007 関連箇所検索

質問に関連する複数文書の該当箇所を抽出し、回答生成へ渡す。

## FR-008 横断回答

複数文書を参照した場合、文書ごとの条件を統合した回答を生成する。

## FR-009 根拠表示

回答に使用した文書、条項、見出し、抜粋を表示する。

## FR-010 ワークフロー結果表示

回答と同時に、業務処理へ利用できる構造化結果を表示する。

必須項目:

- 結論
- 適用条件
- 必要な手続き
- 必要書類
- 承認者または担当部署
- 期限
- 不足情報
- 次のアクション

## FR-011 情報不足の明示

ナレッジ内の情報だけでは判断できない場合、推測せず、確認が必要な情報と確認先を表示する。

## FR-012 回答対象外の制御

ナレッジに存在しない質問、個別の法的判断、医療判断、個人への処分判断などは、回答可能範囲を明示して案内する。

## FR-013 会話履歴

同一セッション内で、直前の条件を引き継いだ追加質問ができる。

ただし、回答根拠は毎回ナレッジから再確認する。

## FR-014 リセット

会話履歴をリセットできる。

## FR-015 利用状況表示

Access Modeに応じて、残り回数、利用回数、処理中状態、制限到達を表示する。

# 9. 回答表示要件

## 9.1 Primary Output

最初に、ユーザーが取るべき結論を短く表示する。  
Status Badgeと結論文を先頭に置き、長い根拠抜粋を結論より上に置かない（Answer Skeleton）。

例:

> 条件を満たせば申請可能です。ただし、午前休の登録後に在宅勤務申請を別途行い、直属上長の承認を得る必要があります。

## 9.2 回答構造

```text
Status Badge
結論
├ 要点（短文3〜5）
├ 必要な手続き / 次のアクション
├ 適用条件（折りたたみ可）
├ 例外・注意点（折りたたみ可）
├ 担当・承認者
├ 期限
├ 不足情報（ある場合は折りたたまない）
├ 根拠（デフォルト折りたたみ）
└ Follow-up Chips
```

## 9.3 根拠構造

```text
根拠1
├ 文書名
├ 条項・見出し
├ 抜粋
└ この根拠が回答に与えた影響
```

## 9.4 Workflow Preview

「このAIを業務フローへ組み込んだ場合」の振る舞いを、次のカードで表示する。

```text
判定: 申請可能 / 条件付き / 要確認 / 対象外
振り分け先: 担当部署
必要アクション: 申請・承認・報告
必要入力: 不足している情報
自動化候補: フォーム初期入力・承認者選択・通知
```

# 10. 回答ルール

AIは次のルールに従う。

1. 指定されたナレッジのみを根拠にする
2. 根拠のない社内ルールを作らない
3. 質問に関係する複数文書を確認する
4. 条件、例外、期限、金額、承認権限を省略しない
5. 規程間に優先関係がある場合は明示する
6. 文書間で内容が矛盾する場合は、矛盾を隠さず表示する
7. 判断に必要な情報が不足している場合は質問を返す
8. 回答ごとに出典を付ける
9. 出典の抜粋と回答内容を一致させる
10. 法的・人事的な最終判断をAIだけで確定しない
11. 「学習済み」「完全に理解している」などの誤解を招く表現を使わない
12. 選択されたナレッジを検索・参照して回答していることを正しく表現する

# 11. Must / Should / Won't

## 11.1 Must

- 高密度なサンプルナレッジパック
- 8文書の事前閲覧
- 文書メタデータと目次表示
- 文書内検索
- ガイド質問
- Intent Rails / Guided Drill-down
- 自由質問（選択式とのハイブリッド合流）
- Answer Skeleton（結論先出し）
- Follow-up Chips
- 複数文書の横断検索
- 根拠付き回答
- 条項・抜粋表示
- 構造化された次のアクション
- 情報不足時の確認事項表示（可能な場合は選択肢）
- 会話リセット
- PC / モバイル対応
- Core経由のAI接続
- Demo固有Adapter

## 11.2 Should

- 回答で参照した文書の強調表示
- 質問ごとの検索中演出
- Clarifying Choiceの充実
- 関連規程マップ
- 回答のコピー
- 回答フィードバック
- 自社文書アップロードへの導線
- 文書差し替え可能なManifest構造
- 回答品質を確認するGround Truthテスト

## 11.3 Won't

初期実装では次を行わない。

- 本番企業の機密文書利用
- 社員アカウント認証
- 部署・役職別の閲覧権限制御
- SharePoint、Google Drive、Box等との常時同期
- 規程の自動改定管理
- AIによる最終的な人事・法務判断
- 申請・承認システムへの本番登録
- 本番監査ログ
- 多言語対応
- 音声入力
- 管理画面からの規程編集
- Demo側でのProvider接続・Trial処理の再実装
- サイト埋め込みチャットランチャーの再現
- LINE公式アカウント / トークUIの再現

# 14. 非機能要件

## NFR-001 正確性

- 回答内の事実は根拠箇所と一致する
- 金額、期限、回数、承認者を改変しない
- 複数文書を参照した場合、すべての主要根拠を表示する

## NFR-002 応答速度

- 質問送信後、即座に処理中表示へ切り替える
- 標準質問では、営業デモとして待ち時間を過度に感じないこと
- 検索、照合、回答生成の進行状態を簡潔に表示する

## NFR-003 可用性

- AI接続失敗時に画面全体を壊さない
- 再試行方法を表示する
- 根拠データの閲覧はAI接続失敗時も可能にする

## NFR-004 セキュリティ

- サンプルデータに実在個人・実在企業の機密情報を含めない
- ユーザー入力をログへ無制限に保存しない
- Provider SecretやAPI Keyを画面・URL・ログへ出さない
- Prompt Injection対策として、ナレッジ本文を命令ではなく参照情報として扱う

## NFR-005 説明責任

- AI回答であることを明示する
- 根拠確認を促す
- 最終判断が必要な領域では担当部署への確認を案内する

## NFR-006 保守性

- サンプル文書はManifestから差し替え可能にする
- 文書内容をUIへ直書きしない
- 検索・AI接続・TrialをDemo UIへ直書きしない

# 15. 成功条件

本デモが成功したと判断する条件は次のとおり。

1. ユーザーが質問前にサンプル規程の内容を確認できる
2. 単一文書質問だけでなく、複数文書をまたぐ質問に回答できる
3. 回答から根拠文書と該当箇所を確認できる
4. AIがナレッジ外のルールを作らない
5. 情報不足時に推測せず確認事項を返す
6. 回答結果から、必要な申請・承認・担当部署が分かる
7. チャットボットだけでなく、業務ワークフローへの組み込み方を想像できる
8. 商談相手が自社規程へ置き換えた利用イメージを持てる
9. 選択式で迷わず進め、結論と次の一手が素早く見える（Conversation UX）
