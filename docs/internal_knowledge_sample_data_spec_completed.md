# 0. 本書の役割

本書は、社内ナレッジAIデモで使用するサンプルナレッジについて、目的、構成、文書内容、相互参照、質問例、期待出力、データ形式、差し替え方法を定義する。

本デモの価値は、情報量の少ないFAQではなく、複数の規程に分散した条件をAIが横断的に照合する点にある。

そのため、サンプルデータ自体をデモ品質の主要構成要素として扱う。

---

# 1. サンプルデータの目的

サンプルナレッジは、次の事実を体験者に理解してもらうために用意する。

1. AIが参照している情報を事前に人間が確認できる
2. 一つの質問に必要な情報が複数の規程へ分散している
3. AIが関連規程を素早く探し、条件や例外を照合できる
4. 回答の結論だけでなく、根拠と次の手続きを確認できる
5. 自社の規程やマニュアルへ置き換えた利用イメージを持てる
6. チャット回答を申請・承認・振り分けなどのワークフローへ接続できる

# 2. 設計原則

## 2.1 架空データ

実在企業の規程、個人情報、機密情報は使用しない。

会社名、部署名、金額、期限、連絡先、制度はすべてデモ用に設計する。

## 2.2 実務らしい密度

各文書には、次を含める。

- 適用対象
- 原則
- 条件
- 例外
- 期限
- 金額上限
- 承認者
- 必要書類
- 申請方法
- 担当部署
- 関連文書
- 違反・未対応時の扱い

## 2.3 文書間の相互参照

各規程を独立したFAQ集にしない。

例:

```text
出張・旅費規程
└ 精算方法は「経費精算・購買規程」を参照

経費精算・購買規程
└ 承認権限は「稟議・承認権限規程」を参照

在宅勤務規程
└ 勤怠登録は「勤怠・休暇運用細則」を参照

情報セキュリティ規程
└ 事故発生時は「相談・事故・緊急時対応ガイド」を参照
```

## 2.4 意図的な判断ポイント

単純なキーワード一致だけでは答えにくいケースを含める。

- 条件によって結論が変わる
- 金額によって承認者が変わる
- 例外時に別文書が適用される
- 原則禁止だが事前承認で許可される
- 必要情報が不足しているため即答できない
- 文書の更新日や優先順位を確認する必要がある

## 2.5 人間が検証可能

すべてのテスト質問に対して、正解根拠となる文書・条項・期待する判断をGround Truthとして用意する。

**バージョン:** 4.0  
**施行日:** 2026-04-01  
**所管:** 経理部・管理部

## 目的

## デモに必要な具体ルール

- 月末最終営業日までの利用分は翌月第3営業日までに提出

- 緊急購入は業務停止・安全上の問題・顧客障害対応に限り、事後1営業日以内に申請

# 5.7 情報セキュリティ・生成AI利用規程

情報分類、社外サービス利用、生成AI利用、端末、事故報告、データ取扱いを定める。

## 主要セクション

1. 情報分類
2. 公開情報
3. 社内限定情報
4. 機密情報
5. 個人情報
6. 外部クラウドサービス
7. 生成AI利用
8. ファイルアップロード
9. 出力内容の確認
10. アカウント管理
11. 端末紛失
12. インシデント報告

## デモに必要な具体ルール

- 顧客契約書、未公開仕様、個人情報は機密情報として扱う

- 条件付きで可能
- 午前半休または子の看護休暇の適用条件を確認
- 午後の在宅勤務申請が承認済みか確認
- 緊急時の当日申請条件を案内
- 勤怠登録方法を案内

### 不足情報

- 対象の子の年齢
- 在宅勤務の対象者か
- 上長承認の有無

## Scenario 02: 出張時の領収書紛失

### 質問

> 大阪出張で3万5千円を個人立替しましたが、ホテルの領収書を紛失しました。精算できますか。

### 参照文書

- 出張・旅費規程
- 経費精算・購買規程
- 稟議・承認権限規程

### 期待判断

- 証憑紛失届と支払記録があれば条件付きで申請可能
- 直属上長承認が必要
- 月内の紛失回数によって部門長承認が追加される
- 宿泊上限を超えていないか確認
- 10営業日以内の精算期限を案内

### 不足情報

- 宿泊地域と宿泊金額
- 今月の証憑紛失回数
- 支払記録の有無

## Scenario 03: 緊急の業務ツール購入

### 質問

> 顧客障害対応のため、10万円のクラウドツールを今日中に契約したいです。何が必要ですか。

### 参照文書

- 経費精算・購買規程
- 稟議・承認権限規程
- 情報セキュリティ・生成AI利用規程

### 期待判断

- 業務停止または顧客障害対応に該当する場合、緊急購入の対象となりうる
- 年間契約総額で承認金額を判定
- 10万円以上のITサービスとして情報システム部レビューが必要
- 顧客情報を扱う場合は情報セキュリティ責任者レビューが必要
- 原則として部門長承認
- 事後1営業日以内の申請が必要

### 不足情報

- 10万円が月額・年額・総額のどれか
- 予算内か予算外か
- 顧客情報を保存するか
- 新規取引先か

## Scenario 04: 顧客契約書を生成AIで要約

### 質問

> 顧客との契約書を無料の生成AIへアップロードして要約してもよいですか。

### 参照文書

- 情報セキュリティ・生成AI利用規程
- 稟議・承認権限規程

### 期待判断

- 原則不可
- 顧客契約書は機密情報
- 未承認の外部生成AIへのアップロードは禁止
- 匿名化だけで足りるかは契約条件と情報内容による
- 承認済みサービス利用、顧客条件確認、情報システム部審査を案内

# 8. ガイド質問セット

## 8.1 単一文書型

## 8.2 複数文書横断型

8. 在宅勤務中にPCを紛失した場合の初動を教えてください

## 8.3 判断・ワークフロー型

9. 顧客資料を生成AIで処理したい場合の手順を教えてください
10. 緊急購入をした後、いつまでに何を申請すべきですか
11. 月次締め後に勤怠を修正する場合の承認経路を教えてください
12. 東京出張で1泊18,000円のホテルを予約できますか

## 8.4 Intent Tree

Conversation UX（P01/P02）用に、上記ガイド質問を Intent Tree の葉として定義する。  
フラットなガイド質問一覧は残し、ツリーは追加データとして Sample Pack に含める。

**配置候補:** `data/sample/towa-corporate-rules-v1/intent-tree.json`

```ts
export type IntentNode = {
  id: string;
  label: string;
  description?: string;
  children?: IntentNode[];
  guidedQuestionId?: string;
  clarifyOptions?: Array<{
    id: string;
    label: string;
    appendText: string;
  }>;
};

export type IntentTree = {
  packId: string;
  version: string;
  roots: IntentNode[];
};
```

### 初期ルート（最大6）

| root id | ラベル | 主な葉（ガイド質問） |
|---|---|---|
| `attendance` | 勤怠・休暇 | 4, 11 |
| `remote-work` | 在宅勤務 | 1, 6 |
| `travel-expense` | 出張・経費 | 2, 3, 5, 12 |
| `purchase-approval` | 購買・稟議 | 7, 10 |
| `security` | 情報セキュリティ | 9 |
| `incident` | 緊急・事故対応 | 8 |

### 制約

- `roots.length <= 6`
- root からの深さは最大3
- 葉は `guidedQuestionId` または `clarifyOptions` を持つ
- `guidedQuestionId` は §8.1–8.3 の質問 ID と一致させる
- 難易度 Level 1/2/3 は質問メタデータとして別途保持し、ツリー階層と混同しない

### Follow-up / Clarifying のサンプル付帯

主要シナリオ（少なくとも Level 2/3 の各1件以上）に、次を定義する。

- `expectedFollowUps`: `open_evidence` / `open_document` / `resend_variant` / `ask_related` など
- `expectedMissingInfoChoices`: 不足情報を選択肢化したときの ID と `appendText`

詳細スキーマは`internal_knowledge_conversation_ux.md` §5を正とする。

# 9. Ground Truth仕様

各テスト質問に対して、次をJSONで保持する。

```ts
export interface GroundTruthCase {
  id: string;
  question: string;
  category: "single_document" | "cross_document" | "workflow" | "insufficient_information";
  expectedStatus: "allowed" | "conditional" | "needs_confirmation" | "not_allowed" | "not_found";
  requiredDocumentIds: string[];
  requiredSectionIds: string[];
  requiredFacts: string[];
  forbiddenClaims: string[];
  expectedMissingInformation: string[];
  expectedActions: string[];
  intentPath?: string[];
  expectedFollowUpActions?: Array<
    "resend_variant" | "open_evidence" | "open_document" | "clarify" | "ask_related"
  >;
  expectedMissingInfoChoiceIds?: string[];
}
```

## 9.1 評価項目

- 必須文書を参照しているか
- 必須事実を回答へ含めているか
- 禁止された推測をしていないか
- 条件付き判断を断定していないか
- 不足情報を正しく挙げているか
- 次のアクションを提示しているか
- 引用元と回答内容が一致しているか

# 10. チャンク・検索用データ仕様

## 10.1 分割単位

見出しと条項を優先して分割する。

目安:

- 1チャンク 500〜900日本語文字
- オーバーラップ 80〜120文字
- 条項を途中で分断しない
- 表は見出しと一緒に保持
- 例外条件を原則から切り離さない

## 10.2 メタデータ

```ts
export interface SampleKnowledgeChunk {
  id: string;
  packId: string;
  documentId: string;
  documentTitle: string;
  version: string;
  effectiveDate: string;
  sectionId: string;
  articleNumber?: string;
  headingPath: string[];
  content: string;
  keywords: string[];
  relatedDocumentIds: string[];
  ownerDepartment: string;
  sortOrder: number;
}
```

## 10.3 検索時の要件

- 文書名だけでなく本文内容で検索する
- 金額、期限、回数などの数値条件を保持する
- 関連文書IDを検索拡張に利用できる
- 同じ文書の隣接セクションを追加取得できる
- 複数文書から根拠を取得できる
- 回答生成へ渡したチャンクIDを記録できる
